The 2026-08-13 ToolboxMD creating-skills benchmark v2 ended in a mixed 1 to 1 result under Codex CLI 0.147.0 with gpt-5.6-sol at medium reasoning. Neither creator demonstrated better downstream quality, so the frozen ToolboxMD candidate is not promoted. The built-in creator remains the current default only because the challenger did not clear the predeclared two-win gate, not because the experiment proved general built-in superiority.

Two daily-use cases qualified through the same-model no-skill arm. Meeting follow-ups passed 2 of 8 critical checks without a target skill; both creator-produced skills passed 7 of 8 and generated byte-identical outputs. Their one shared failure came from an under-specified exact fixture that omitted source terminal punctuation. Weekly status deck passed 7 of 8 without a target skill; both generated skills passed 8 of 8. Built-in won the meeting case only on one-run cost, 18,550 versus 21,609 runtime tokens. ToolboxMD won the deck case on the same low-confidence tie-break, 23,982 versus 30,228. Four of four natural positive prompts loaded the full target SKILL.md before output creation. Zero of four exposed target skills loaded in related near-miss prompts.

ToolboxMD's demonstrated strength is its compact activation metadata. Its descriptions were 29.5% and 39.2% shorter with the same observed positive and near-miss behavior. Its demonstrated weakness is package and authoring cost. SKILL.md grew 11.6% and 14.1%, packages grew 29.7% and 53.9%, and authoring took longer in both cases. Default eval artifacts and delivery checks did not improve downstream quality in this sample.

The next ToolboxMD creator should preserve the compact description pattern, emit current-directory-independent script commands, move comparative and repeated eval ownership to toolboxmd-benchmarking-skills, count always-read references as activated core, make Git delivery checks conditional, and enforce a measured deletion pass. It must be frozen as a new candidate rather than mutate the retained v1 snapshot.

The first four authoring attempts were discarded before downstream use because both built-in attempts wrote Python bytecode under the protected creator tree. Protocol revision 2 disabled bytecode writes and repeated all four arms symmetrically. The reserve spreadsheet case did not run because it required five sessions and only one remained below the 17-session ceiling. Sixteen decision sessions used 728,273 uncached-input-plus-output runtime tokens over 2,759 cumulative seconds.

Known limitation: supporting grader and event-audit scripts were not included in the pre-run protocol commitment. Their at-result hashes and retained outputs are inspectable, but the commitment alone cannot prove that every supporting tool stayed byte-identical during execution. Future benchmarks must freeze the complete measurement chain and use paired repeats when one-run cost alone determines a case.
