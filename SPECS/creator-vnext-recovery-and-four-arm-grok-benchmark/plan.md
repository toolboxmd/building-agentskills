# Creator vNext recovery and four-arm Grok benchmark

## Outcome

Recover `toolboxmd-creating-skills` vNext as a standalone, reviewable product on
top of current `origin/main`, preserve only the minimum honest lineage from the
inconclusive benchmark, and run a pre-registered four-treatment Grok authoring
comparison after the final Creator candidate is frozen.

This plan separates three decisions:

1. whether Creator vNext is mechanically safe and ready for merge consideration;
2. what the known Grok brief diagnoses about four frozen Creators;
3. whether later held-out evidence supports promotion.

No pull request may merge without separate explicit user approval.

## Approved decisions

- Park pull request 1 unchanged and unmerged. It remains the inspectable source
  for the failed benchmark and must not be cited as a creator or cost winner.
- Make pull request 2 standalone on current `origin/main`; do not make its
  engineering readiness depend on the known Grok brief.
- Keep the broad custom validator, but freeze its responsibility at the
  documented canonical ToolboxMD-generated subset and package policy. It is not
  a general YAML, CommonMark, shell, or helper-language parser.
- Land the two current exact-HEAD P2 corrections: required `SKILL.md` entry
  safety before reading and Hermes config state closure on dedent.
- Set the internal Creator package cap to exactly **48,000 bytes**. This is a
  one-time policy revision, not a platform limit and not permission for
  unbounded validator growth.
- Compare four frozen creator treatments on the Grok brief: legacy ToolboxMD,
  early vNext at `bfbd679`, final vNext, and the exact current built-in Codex
  `skill-creator`.
- Use one shared frozen authoring model and harness across all four treatments.
  A later Codex-native run, if desired, is a separate realism check and not part
  of the paired creator comparison.
- Keep the historical raw Grok and the acceptance-refined current Grok as
  unranked artifact references.
- Keep Grok automatic review disabled. New real Grok calls require separate
  authorization.
- Do not create new wiki captures during this recovery unless separately
  authorized. Preserve every existing pending capture byte-for-byte.

## Phase 1: recover and freeze Creator vNext

2. Preserve the two tracked P2 changes and all untracked user files.
3. Create an explicit recovery reference before rewriting branch history.
4. Fetch remote refs and verify that the expected remote heads have not moved.
5. Stop if any unknown tracked change, remote movement, or concurrent branch

### 2. Finish the two exact-HEAD P2 corrections

bounded timeout for FIFO/device fixtures.

## Phase 2: pre-register the four-treatment Grok diagnostic

### Treatments

| Arm | Frozen treatment | Role |
|---|---|---|
| A | Legacy ToolboxMD Creator | Historical ToolboxMD baseline |
| B | Early vNext at `bfbd679` | First vNext implementation |
| C | Final exact reviewed vNext | Recovered candidate |
| D | Exact current built-in Codex `skill-creator` | Independent built-in baseline |

Freeze exact hashes for A, B, C, and D before any authoring run. Arm C cannot
start before Phase 1 completes.

### Unranked references

- the byte-retained historical raw Grok package;
- the current acceptance-refined Grok package.

Apply the same deterministic artifact tests to both. A fresh arm B versus the
historical raw package is only a harness-drift and reproducibility observation.
Neither historical package contributes to the creator ranking or authoring-cost
comparison.

### Common authoring conditions

Every ranked arm receives the same:

- frozen Grok brief and local source packet;
- authoring prompt;
- model and reasoning effort;
- tool surface;
- time and token budget;
- filesystem read/write boundary;
- network policy;
- clean environment and fresh context;
- output contract.

Prevent every arm from reading the other Creators, generated candidates,
historical Grok packages, user configuration, unrelated skills, repository
history, or credentials. Use anonymous arm labels for grading, while reporting
that package layout can still fingerprint a Creator.

### Mandatory isolation and abort gates

The benchmark must retain independently inspectable evidence for:

- sanitized environment variables;
- allowed filesystem reads;
- output-only filesystem writes;
- syscall-level network enforcement;
- actual command cwd;
- command and tool event traces;
- immutable treatment, input, harness, and grader hashes.

If any ranked arm lacks this evidence or crosses a boundary, stop the comparison
and report it as ineligible. Do not grade a winner from the remaining arms.

### Neutral evaluation

Freeze the winner rule before outputs exist. Evaluate:

- portable Agent Skills validity through a neutral or official checker;
- frozen Grok contract compliance;
- fake-CLI invocation and failure behavior;
- positive triggering and difficult near misses;
- prompt-file, environment, timeout, process-tree, stop-reason, error, and tool
  denial behavior;
- downstream procedure adherence and usefulness;
- description, activated-core, file, and package cost;
- authoring duration, tokens, commands, Git inspection, and unjustified files.

Report custom ToolboxMD-validator compatibility separately. Its policy, the
48,000-byte Creator cap, or stylistic resemblance to ToolboxMD cannot decide the
winner.

### Pre-registered decision rules

- A critical safety or contract failure disqualifies that arm from being a
  recommended artifact, but does not erase its retained evidence.
- The known Grok brief is diagnostic only because it influenced vNext. It cannot
  establish general superiority, production promotion, or a default Creator.
- Stage 1 uses one fresh run per ranked arm as a diagnostic screen.
- A blind no-creator run may qualify task non-triviality but is not a fifth
  ranked Creator.
- Before Stage 1, record the exact contender rule for held-out admission.
- If observable utility ties and cost is the only separator, run exactly one
  pre-authorized paired repeat. Do not add repeats after seeing an inconvenient
  result.
- Publish inconclusive as a valid result when isolation, variance, or score
  boundaries do not support a winner.

## Phase 3: held-out promotion evidence

After the final vNext freeze and Stage 1 results, freeze a compact set that was
not available during Creator authoring. It must cover at least:

- an unseen paraphrase of the explicit consultation request;
- realistic positive and difficult near-miss triggering;
- malformed Grok structured output;
- incomplete or invalid stop reason;
- an observed tool-call attempt;
- unrelated runtime-extension isolation.

Run held-out only for treatments that satisfy the pre-registered contender
rule. A new real Grok call, dedicated authenticated profile test, or automatic
mode acceptance requires separate user authorization.

Possible final outcomes:

- **promote vNext:** held-out evidence supports a bounded improvement without a
  critical regression;
- **retain vNext as candidate:** evidence is tied, mixed, noisy, or diagnostic
  only;
- **reject vNext:** it introduces a critical regression;
- **ship Grok independently:** the refined product may be useful even when the
  Creator comparison is inconclusive.
